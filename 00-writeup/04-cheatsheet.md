# 04-cheatsheet writeup  

这道题和前面每一道都不一样：我要优化的对象不是代码，而是一个 AI 考生。规则是让我从两个模型（Qwen3.8-27B 和 DeepSeek V4 Flash）和两个算子（bitmatrix 和 fft）里各挑一个，交一份不超过 1200 token 的 SKILL.md 当"小抄"，指导这个模型在 20 分钟、最多 16 轮里把算子改快，跑完还有 10 分钟收尾。同一份小抄跑两次独立运行，取高的那次算分。我挑的是 deepseek-reasoner 加 fft。评测机是坤鹏 920（ARM64），单线程、不许运行时分配内存、不许调 FFT 库。  

拿到题我先让AI把评分公式读了一遍，这题的分几乎全写在公式里：最终分等于 100 乘以 min(1, 性能分 P × 长度倍率 m)。性能分 P 是加速比换算出来的，加速比要超过 2 才开始得分，到 4 左右满分，不到 2 一律 0 分；长度倍率 m 则是资料总长不超过 400 token 时是 1.5，800 token 时 1.0，1200 token 时 0.5。这一眼就把我的目标改写了：当 m=1.5 的时候，P 只要 0.667 就是满分，换算成加速比大概只要 3.3 到 3.4 倍。也就是说，把 agent 从 3.4 倍推到 5 倍是一分不加的，而手册每多写 100 token 是实打实扣分。这是我第一次遇到"越短越好"的优化题。  

但 3.4 倍到底难不难，光看公式看不出来。所以在让 agent 上考场之前，我先在坤鹏计算节点上，把 fft 从起始版本到成品亲手搭了一遍阶梯，每一步都实测（公开算例是 16×256 和 8×1024 两组）：起始版是 92.37 和 228.21 微秒；第一步把旋转因子预先做成查表，1.6 到 1.7 倍；第二步把复数拆成实部虚部两条数组再向量化，2.4 到 2.7 倍；第三步改成跨 batch 的布局加 Stockham 自排序，3.3 倍；最后再叠上 radix-4 和 NEON 转置，两个算例分别是 3.72 和 3.63 倍，刚好越过满分线。这一步也是我第一次真看懂 FFT 到底怎么向量化：要让向量的一条 lane 装"同一个下标、不同 batch"的数据，而不是装一个变换内部的四个点——因为一次调用本来就有 16 个（或 8 个）互相独立的变换，摆成 re[i*8+l] 之后，8 个 batch 正好是两条互不依赖的 NEON 链，四条 lane 共享同一个旋转因子，中间不用做任何 lane 之间的搬运。还有个反直觉的实测结论：8 条 lane 是甜点，16 条反而更慢，因为工作集超过了 L1 缓存。这几条配方，就是后来手册里的四级台阶。  

手册要短，所以我不能每改一版就上集群测一轮——官方测试一轮要 25 到 45 分钟，还烧 API 额度。于是我在本地用官方那份冻结的词表复现了计数，拿一个已知是 382 token 的版本对过，数字一模一样，从此改一版量一次只要几秒钟。顺手还称出一个反直觉的结论：表达完全相同的内容，英文比中文省 26% 的 token，尽管字符数多了 53%，因为词表对英文技术文本的压缩率高得多。另外还踩了个提交级的坑：英文 description 里写 fft kernel: cross-batch 这样一句，那个半角冒号加空格会被 YAML 当成键值分隔符，提交直接被 REJECTED。  

官方测试我前三轮跑出来是 0 分、23.8 分、0 分。第二轮那次是唯一成功的：agent 交出来的 kernel 是 0.062 毫秒，相对原版的 0.145 毫秒大约 2.3 倍，正好落在手册里写的"前三步约 2.4 倍"那一级上，两个算例各自 2.18 倍和 2.47 倍，代进公式 P=0.159，乘上 1.5 的倍率就是 23.8 分，跟脚本输出对得上。第三轮我把手册改成了"一步到位"的英文版，一口气把跨 batch 布局、Stockham、radix-4 全写上去，结果 0 分，而且是最难看的那种 0 分：两个 agent 运行前后的 kernel 文件 sha256 一模一样，一行代码都没改，日志里的 changed_kernel 字段是 false。翻它的运行记录才看明白，agent 那 20 分钟的墙钟预算全被读文件和它自己的长时间卡顿吃光了，它把 tools 底下的脚本挨个读了一遍，中途还想去够被隐藏的 spec.yaml，两次 ls 被沙箱拒了。反过来看第二轮成功的那次运行：整场只用了 13 次工具调用，就把 kernel 写完并且正确性通过了。原来成败的分界不是手册写得好不好，是 agent 多快开始动手改 kernel.cpp。  

顺着这条线还挖出一个我自己挖的坑：agent 的沙箱对 bash 有白名单，实测只放行四条命令（bash tools/build.sh、bash tools/test_candidate.sh、bash tools/profile.sh、bash tools/vec_report.sh），连 ls 都不放，而我第二版手册的最后一行写的偏偏是 tools/check.sh 和 tools/bench.sh。手册里提到哪个脚本的名字，agent 就会去读它、试它——是我自己把它带到沟里的。  

所以最后一版我改成了"阶梯"：手册不再一口气讲完所有手法，而是一级一级往上爬，每一级写清楚"做完大约几倍"，并且立了三条规矩——验证只跑一条命令 bash tools/test_candidate.sh（它一次就把编译、正确性、计时全做了）；不要去读 tools 下的脚本，直接改 kernel.cpp；某一级连续两次正确性不过，就把上一版能跑的代码写回去、立刻停手，因为评测器不会自动回滚，最后留在工作区的那份代码才算数。还有一个看源码得来的细节：手册正文不会自动喂给 agent，它一开始只看得到 name 和 description 这两行，要自己决定去不去加载整份手册，所以那行 description 得写成钩子。定稿这一版是 506 token，倍率 1.37，比中文版的 1.5 少了差不多 9%，等于把自己从"免费区"里挪了出来。这是个我认下的取舍：用一点倍率，换 agent 别再把时间浪费在读文件上。  

最终成绩：OJ 正式评测 38 / 100。比第二轮的 23.8 高，说明阶梯版确实推着 agent 多爬了一两级；但按倍率反推，它的性能分只有 0.28 左右，离"越过满分线"还差一大截——手册里最要紧的那级台阶（跨 batch 向量化），它还是没爬上去。  

## 总结  
这题让我学到三件事。第一，评分公式一定要读一遍：这题的分几乎全写在公式里（长度倍率的免费区、起算线和满分线的位置），凭"越快越好"的直觉去写，只会写出一份又长又慢的手册。第二，AI 的行为本身也是要用实测去摸的：同一份手册，这一轮 0 分，下一轮 23.8 分，靠猜是猜不出来的，得去看它的运行日志——读了几个文件、调用了几次工具、有没有真的改代码；我这次能搞清楚翻车翻在哪，全靠 changed_kernel 这个字段。第三，写文档也是一种工程：正文写得再漂亮，agent 不去加载就等于没写，而且它会照着字面行动——我在手册里写哪个脚本的名字，它就去读哪个脚本。
