# 03-accelerate writeup  
这是我着手的第一道比赛题目，在这个阶段我对于超算的各种优化方式、优化思路和直觉都还约等于零，所以我在这道题上花了很多时间慢慢审题，让AI带着我理解一道性能优化题目的做题流程是怎样的。在我看来，这道题计算量最大的部分就是高斯距离项和正弦投影项那一部分，所以这是矩阵运算的并行优化，要利用并行计算和分块计算等等来优化。又由于最近我C写得比较多，也简单学了一点openmp的知识，而python代码的解释器开销特别大，所以自然想到用C代码来写。  

我把我的思路————openmp并行化、C重写告诉AI让他帮我实现，于是我便开始了此生第一次的python内嵌C代码体验。其实内嵌C这个思路可能也在README里面一句测试环境装好python3.devel有所暗示，不知道是不是我自作多情。    

AI先用numpy写了一版兜底代码，用了分块优化，性能相较于原先的三层循环版本已经有所提升，这是在C内核编译失败的时候为了防止零分写的。由此我也得到了优化的第一步经验：先获取一个最小分数baseline，然后根据后面的优化不断和baseline比较、更新，确保优化的稳步提升。  

然后开始在scratch里面写一个kernel.c，先用最朴素的三层循环写一个内核，用于测试内嵌C的可行性。我也学到了这种一步一步慢慢优化的方式：不要一口气做太激进的操作，先写一些小的简单的kernel测试环境。在此期间AI也写了一些用于验证正确性的test_kernel.c、test_solver.py等门禁代码，这也教会了我优化的首要前提是确保正确性，代码经过优化之后得到的结果精确性必须在可容忍范围内，否则这样的优化没有意义。在初版float32累加的时候准确性牺牲也确实有出现门禁跑不过的情况，改成double解决了这个问题。

发现内嵌可行之后，就开始openmp并行化。注意到矩阵的Q维度是独立的，所以用#pragma omp parallel for schedule(static)利用多线程可以很大程度上加速计算。理论上16线程可以将时间压缩到十六分之一，但在实践中并没有如此理想，只有5.3x，这也是我学到的一个新的知识点：Amdahl定律，静态调度下最慢的核决定墙钟时间（系统加速比受限于系统中无法并行的部分）。  

接着我尝试在算法部分突破。AI提示可以用手写的exp、sin来替代原来的expf、sinf，以节约不必要的精度开销。AI给的代码是利用范围规约和多项式逼近+位操作：  
exp：t = k·ln2 + r → e^t = 2^k·e^r；k 用 rint 取整，2^k 用 ldexp 直接写指数位  
sin：t = k·π + r → sin(t) = (−1)^k·sin(r)；奇函数换元 u = r² 使多项式次数减半  
但实际测试下来却比原来的版本还要慢，汇编级别的诊断是手写版本有数据相关（符号、奇偶判断）导致分支预测失败，所以性能还不如glibc的expf/sinf。但是这个尝试是有益的，因为它提供了多项式框架，为后来向量化方案打下地基。  

然后我做了一些编译器旋钮优化。一开始尝试    `-funroll-loops`+`#pragma GCC unroll 8`(d循环)；c循环上的omp simd实测证明是no-op。遂删除。  
原理是展开后编译器可以同时发出4~8各互不依赖的expf/sinf，互相掩盖延迟。优化的结果是单线程从8.261s→4.549s；门禁没问题。  

这时候已经上传oj跑了一次，分数差不多了。接着我尝试分块转置和向量化多项式。分块是将总数据分成64块，将数据流量降到64分之一，这一步操作是成功的，门禁通过，性能也没有下降。但是在尝试向量化多项式的时候AI的代码多次出现bug，出于做题效率考虑我没有继续这方面的优化，转战其他题目。  

## 总结
这是我的程序优化初体验，个人感觉是学到很多的。我学会了拿到题目先尝试建立门禁，拿到一个最小得分的baseline然后在基础上一步步优化；学到了独立重复运算可以并行优化，也学会分析并行优化在实践中不理想的可能原因；还学会了在python代码动态编译C还有降级路径的保底，等等。总而言之，这是一个很好的入门体验。
