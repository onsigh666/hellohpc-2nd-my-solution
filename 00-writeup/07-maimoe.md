# 07-maimoe writeup  

这道题是一个 MaiMoe 谱面导入模拟器。程序分两种进程：一个主进程（maimoe）负责把谱面派下去，好几个 worker 进程（maimoe_kernel）负责干活，每张谱面都要做哈希、编码和渲染。我能改的只有两个文件，一个是 solution/Kernel.cpp（worker 的入口），一个是 solution/KstroParam.toml（运行参数），主进程和引擎的源码都是只读的。  

拿到题目我先把题面审了一遍，审完有两点印象比较深。一是可改的文件清单里特意放了一个参数文件——题目允许改参数，说明参数本身就是留给选手的旋钮，很可能一拧就有效果；二是题目另外配了一个独立的 maimoe_check 来判定正确性，那 kernel 里面自己再做一遍校验多半是多余的，这部分代码应该可以直接砍掉。至于评测口径算的是 wall time 而不是 CPU 时间（所以把活摊到多个进程上是稳赚的），以及 Sample4 一个人占了 50% 的权重（力气该优先花在它身上），这两条是我做完之后回过头AI跟我说了我才反应过来的，审题的时候并没有这个敏感度。不管当时有没有意识到，后面我的优化基本上就是围着这几点做的。  

第一步和 03 一样，先跑一个 baseline。题目自带 tools/test.sh，评测口径和正式评测一致，我在本地把四个算例全量跑了一遍，记下原始时间，也顺便知道自己大概在什么水平。跑出来的分数很低，我就让 AI 带着我把代码读了一遍，特别是主进程是怎么调度 worker 的。读完发现，这题的并行框架题目作者早就写好了，只是默认参数把它"按住"了：cpu_workers 默认是 1，等于八个核只派了一个 worker 干活。我把它改成 8，本地分数一下子从 0.2 分涨到 53.4 分。  

另一个参数是 pipeline_mib，它的作用是限制"同一时刻所有 worker 手里没做完的谱面字节总数"，默认只有 1MB，对大算例来说等于又把 8 个 worker 卡成了串行。我把它提到 64MB，本机 Sample4 快了 6.2%，集群上也有 3.9%。  

然后我把 worker 入口里的多余代码删掉了，这种只靠删代码就能提升性能的情况我是第一次遇见。原来的 Kernel.cpp 在调用引擎之前，会自己把输入谱面重算两遍 SHA-256 来校验完整性，还做了一些格式扫描、逐字符拷贝、输出清零之类的事。由于引擎是确定性的，正确性又有独立的 maimoe_check 判定（审题时就留意到的第二条），这些操作实际上都没有必要。我把它们全删掉，直接调引擎把结果写进输出缓冲区，顺带省掉了每张谱面的堆分配。改完 checker 全部通过，本地从 53.4 分到 61 分。删代码也算优化，这一点我以前没想过。  

接着是调度的顺序，这是我在代码这边改得最"像优化"的一处。主进程发给 worker 的谱面顺序是由 schedule_policy 决定的，默认是 manifest，也就是照着清单顺序发。我把它改成 size_desc，按谱面字节数从大到小发：最大的谱面第一个开工，最小的最后去填缝。道理是八个 worker 一起干活，总有人先干完；如果最后开工的恰好是最难的那张，剩下七个干完就只能干等着它收尾（我学到这个叫尾部效应，tail effect），这段时间是白费的。让重活排前面、小活排后面，收尾这一段就能被填满。集群实测总分从 64.74 涨到 64.99，Sample4 从 3737.8ms 降到 3702.6ms。  

不过这中间我绕了一下。我最先用的排序依据不是字节数，而是数据里自带的一个"工作量"字段（work_units），我当时觉得"工作量"听起来比"字节数"更能代表谁重谁轻，就按它从大到小排（这个策略叫 work_lpt）。本机模拟预测这样能让 Sample3 省 9%，上集群一测只省了 0.2%，几乎没用；换成按字节数排之后才有提升。集群上三个配置我各跑了一轮：manifest 64.74、work_lpt 64.86、size_desc 64.99，最后选了 size_desc。这件事教了我两点：一是我以为更"聪明"的指标不一定真的更贴近实际，work_units 在这份数据里不是"谁重谁轻"的好代理；二是本机模拟出来的预测不能当真，得上集群实测了才算数。  

后面还有几个教训。一是本地测的不算数：本地创建一个 worker 进程要 10ms 左右，集群只要 1ms 左右，所以 Sample1 本地要跑 195ms、集群 87.5ms 就满分了，跟进程创建有关的结论都不能信本地。二是我以为把输出攒一批再写能省系统调用（我以为这也是题目留的杠杆），结果反而更慢，因为写文件本来就先走页缓存，系统调用不是瓶颈。三是我试着用 ARMv8 的哈希硬件指令替换软件 SHA-256，测下来吞吐是软件实现的 5.5 倍（875 vs 160 MB/s），但改了四轮正确性自检都没过，哈希错一位整个算例就是 0 分，只能暂时放弃。  

## 总结  
这道题和 03 不太一样：优化不一定是从算法和并行开始的。先搞清楚程序的结构——谁在派活、谁在干活、哪些参数把它按住了、哪些代码是白干的——可能比一味地改算法更快见效。我还是先建 baseline 再一步步和它比，也再一次被提醒性能结论要以集群实测为准。最终成绩：集群自测 64.99 / 100，OJ 正式评测 72 / 100。
