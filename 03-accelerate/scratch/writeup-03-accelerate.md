# 03-accelerate「核场响应加速」Writeup 素材整理

> 心路历程完整脉络：审题 → 思路演进 → 数据 → 教训。正式 writeup 的原料，可扩写成文。

## 1. 审题

**公式**：

```
out[q] = Σ_c [ w_c·exp(−s_c·‖x_q−μ_c‖²) + b_c·sin(t_c·(x_q·v_c)) ]
```

- 高斯径向基项（Gaussian RBF kernel）+ 正弦投影项，逐点对 C 个中心求和
- 规模：Q ≈ 10⁵、C ≈ 10⁴、D ∈ {16, 32} → 计算量 O(Q·C·D) ≈ 3.2×10¹⁰ 次乘加
- 数据约 50 MB，可全部驻留内存

**审题得出的三个关键观察**：

1. q 之间完全独立 → 天然可并行（为 OpenMP 埋下伏笔）
2. 输入 float32、judge 保证 C 连续 → 可直接交给 C 指针，无需转换
3. scales 全为正 → exp 参数恒 ≤ 0，无上溢分支（为手写 exp 简化铺路）

## 2. 思路演进（时间线 + 每步动机 + 数据）

### 第 0 步：理解基线，先建门禁
- 题目给的三层 Python 循环是"故意慢的正确基线"
- 第一件事不是优化，而是写 `scratch/test_solver.py` 三关门禁（正确路径 ×2 + 降级路径 ×1），比值 = max|误差|/容差
- 教训 #1：**先有裁判，再比赛** —— 之后每一版都先过门禁再谈速度

### 第 1 步：numpy 向量化（降级路径）
- 分块（block_size=256）+ broadcasting 算距离矩阵 + einsum 算点积
- 门禁比值 0.0167；认识到临时数组内存压力、归约粒度受限

### 第 2 步：内嵌 C 内核
- solver.py 在 import 时把 `_C_SOURCE` 动态编译成 .so（gcc + ctypes），编译失败自动降级 numpy——性能与稳妥性兼得
- 单点三层循环逐点计算，摆脱解释器开销
- 门禁：0.0049 / 0.1357 / 0.0167

### 第 3 步：数值正确性——float32 累加翻车
- 初版 float32 顺序累加：大题比值 1.39 > 1，**门禁拦截**
- 原因：10⁴ 级求和的舍入误差累积超出 float32 精度
- 修复：累加器全换 double（rr / pp / acc），中间量保留 float32 → 比值 0.1357
- 教训 #2：先正确，后快

### 第 4 步：OpenMP 并行
- q 维独立 → `#pragma omp parallel for schedule(static)`
- static 调度保序，数值与串行逐位一致（门禁一字不差）
- 16 线程 8.297 s → 1.569 s，只有 5.3×——开发机是大小核异构 CPU（6P+8E+2LP），静态调度下**最慢的核决定墙钟时间**（木桶效应 / Amdahl 定律）

### 第 5 步：超越函数的深入探索（本场最大的学习收获）
- 数学原理：范围归约（range reduction）+ 多项式逼近（polynomial approximation）+ 位操作精确回补
  - exp：t = k·ln2 + r → e^t = 2^k·e^r；k 用 rint 取整，2^k 用 ldexp 直接写指数位
  - sin：t = k·π + r → sin(t) = (−1)^k·sin(r)；奇函数换元 u = r² 使多项式次数减半
  - 切比雪夫拟合（Chebyshev fit）：同阶数下误差比 Taylor 小 ~46×
  - 用 Python 逐位复刻 C 逻辑验证误差：exp 最大相对误差 2.56e-9，sin 最大绝对误差 1.14e-10，远小于 float32 的 1 ulp
- 结果：x86 上标量手写版反而比 glibc 的 expf/sinf 慢（sin 慢 ~2×）
- 汇编级诊断（objdump）：glibc 用 IFUNC 分发到 AVX2+FMA 版本；手写版有数据相关分支（符号、奇偶判断）→ 分支预测失败；无 FMA；expf 调用导致寄存器溢出
- 教训 #3：机器相关的性能直觉完全靠不住，**必须实测**；x86 的失败原因（分支/无 FMA）在 ARM 上不成立
- 决定：回退 expf/sinf，但保留多项式框架——它后来成为向量化方案的地基

### 第 6 步：编译器旋钮——延迟隐藏
- `-funroll-loops` + `#pragma GCC unroll 8`（d 循环）；c 循环上的 `omp simd` 被实测证明是 no-op（已建议删除）
- 原理：展开后编译器可同时发出 4~8 个互不依赖的 expf/sinf，互相掩盖延迟（latency hiding）；运行时间 = max(吞吐×数量, 延迟×链长)，展开削短后者
- 结果：单线程 8.261 s → 4.549 s（1.82×）；16 线程 1.569 s → 0.409 s（3.84×）；**门禁仍一字不差**
- 教训 #4：我此前预测"旋钮天花板 10~20%"——错了，因为只按吞吐算账、忽略了延迟

### 第 7 步：瓶颈定位——分解基准（decomposition benchmark）
- 宏注入把内核拆成 6 个变体分别计时：内层算术 48~53%，超越函数 47~52%
- 此前"超越函数占 75%"的猜测被推翻——教训 #5：**先测再猜**

### 第 8 步（进行中）：内存带宽分析
- 当前版本每个点重读全部中心数据：2.6 MB/点 × 98304 点 = **257 GB 总流量**
- 本地 16 线程已跑到 ~105 GB/s，贴近本机带宽上限（这是 16 线程只有 11× 而非 16× 的原因之一）
- 结论：瓶颈会随机器迁移——本地 2.45 s（全量）在 32 核服务器上预计 1.5~2.0 s，从计算瓶颈变成带宽瓶颈（memory bandwidth）
- 备好的下一步：分块转置（BQ=64 点共享中心数据，流量 ÷64 → 预计 0.8~1.2 s）+ 向量化多项式（4 车道 SIMD，GNU vector extensions 可移植到 ARM NEON，float32 车道、分支全消）

| C 内核 + OpenMP | 8.297 s | 1.569 s | 0.0049 / 0.1357 / 0.0167 |

## 4. 方法论总结（writeup 的亮点：失败与教训）

1. **先有门禁再优化**——每次改动先证正确性，再谈速度（三关模式可复用到所有题）
2. **先测再猜**——三次直觉翻车：手写超越函数预期 1.5× 实际更慢；旋钮天花板预期 10~20% 实际 1.8×；占比猜 75% 实测 52%
3. **瓶颈会跟着机器搬家**——本地大小核 vs 服务器均匀核；带宽 vs 计算；优化决策以目标机器为准
4. **延迟 ≠ 吞吐**——时间由 max(吞吐×数量, 延迟×链长) 决定
5. **数学工具包**——范围归约 + Chebyshev + 位操作回补 + Python 逐位复刻验证：手写超越函数的通用框架
6. **动态编译 + 降级路径**——import 时编译 C、失败自动降级 numpy：性能与稳妥性兼得
