## 一、计分规则（为什么要拼 S=3.5）

单题得分 = `clamp((S - B) / (T - B), 0, 1)`，其中 S = 起始版耗时 / 你的耗时。

fft 两个用例的公开 B/T：

| 用例 | B（起算） | T（满分） |
|---|---|---|
| 16×256 | 2 µs? → 实测用 starter 92.37 µs | 需 S ≥ 4 才满 |
| 8×1024 | 同上，starter 228.21 µs | 同上 |

总 P = 两用例得分取平均，再乘 token 倍率 m，最后 `min(1, P×m)`。

**m 的算法**：`m = 1.5 - max(0, N-400)/800`，N 是手册的官方 token 数（含记录开销 34）。
- N ≤ 400 → m = 1.5
- N = 800 → m = 1.0

所以 **N ≤ 400 时，P 只要 ≥ 1/1.5 = 0.667 就是满分**，换算成加速比就是
S ≈ 3.27（16×256）、S ≈ 3.40（8×1024）。

**结论：目标不是"越快越好"，是"两个用例都到 S≈3.4"。** 超过 3.4 的优化不再加分，
但手册多写 100 token 会实打实扣分。

## 二、四个关键手法（按实测收益排序）

本地在坤鹏（Kunpeng）计算节点上实测的阶梯，每一步都是实测、不是估计：

| 版本 | 做了什么 | 16×256 | 8×1024 | S₁ | S₂ |
|---|---|---|---|---|---|
| f0 | starter | 92.37 | 228.21 | 1.00 | 1.00 |
| f1 | 旋转因子查表 | 56.74 | 130.99 | 1.63 | 1.74 |
| f2 | SoA + SIMD | 39.32 | 83.72 | 2.35 | 2.73 |
| f5 | **跨 batch + Stockham** | 28.03 | 73.35 | 3.30 | 3.11 |
| f8 | **+ radix-4** | 26.15 | 64.96 | 3.53 | 3.51 |
| f9 | + 转置向量化 | 24.83 | 62.91 | 3.72 | 3.63 |

### 1. 向量化要"跨 batch"，不是"跨蝶形"

这是**最大的一次跳跃**（f2 → f5，S 从 2.35 到 3.30）。

**直觉做法**（错的方向）：在一个变换内部，让向量的一条 lane 装下标 0、1、2、3 的四个点。
问题：长度 256 的 FFT 第一层只有 128 组、第二层 64 组……**早期几层根本凑不满 4 条 lane**，
而且不同 lane 的旋转因子不同，需要 lane 间搬运（shuffle），在 NEON 上很贵。

**正确做法**：`batch = 16`（16×256）意味着有 **16 个互相独立的变换**。让向量的一条 lane
装"同一个下标、不同 batch"的数据：

```
布局：re[i*8 + l]   i = 下标(0..255), l = batch(0..7)
一行 8 个 batch = 2 个 NEON 向量 = 2 条互相独立的依赖链
```

好处：4 条 lane 天然共享**同一个**旋转因子（twiddle factor），一次 `vdupq` 广播即可，
零 lane 间搬运。而且所有层都满载，跟长度无关。

**为什么是 8 不是 16**：实测 f7（16 lane）= 27.78 µs，f5（8 lane）= 28.03 µs，几乎无差别。
但 16 lane 时单分组工作集 = 256×16×4B×2 = 32 KB > L1D（一般 32–64 KB，含其他数据就溢出）。
8 lane 是甜点。**注意：这里是实测推翻直觉**——"越宽越好"在这里不成立。

### 2. Stockham 自排序：省掉一整趟数组扫描

**教科书做法**：位反转置换（bit-reversal permutation）→ 逐层蝶形。
位反转要**单独扫一遍整个数组**，而且访存是随机跳的，cache 完全不友好。

**Stockham 做法**：把重排**折进每层的读写地址**里。递推：

```
for s = 1..log2(N):
  h = 2^(s-1)              # 半边长度
  j < N/(2h), k < h        # 循环边界
  w = w[k]                 # 旋转因子，只跟 k 有关
  u = cur[j*h + k]         # 取两行
  v = cur[j*h + k + N/2]
  nxt[j*2*h + k]     = u + w*v    # 写到两处
  nxt[j*2*h + k + h] = u - w*v
```

不变量：`u + v` 的类型永远是 `u - v` 的类型。写完最后一层自然就是正序。

实测：f4（Stockham，4 lane）比"位反转 + 蝶形"的等价版本快 —— 省掉的是对**整个数组**的一趟
读+写。对 256 点来说是 8 层里的 1 层，对 1024 点是 10 层里的 1 层，约 10% 的量级，但因为是
随机访存，实际收益更大。

### 3. radix-4：把两层合并成一层

radix-2 每层都要把整个数组读一遍写一遍。radix-4 一次处理 4 个点，等于**两层并一层**：
256 点从 8 遍降到 4 遍，1024 点从 10 遍降到 5 遍。

**这里有两个坑，我实际踩过（第一版正确性 FAIL）**：

1. **输出偏移顺序是 0, 2g, g, 3g —— 第 1、2 个是互换的**。
   自然的 DIT 顺序是 `p±w1q, r±w3s`，但 Stockham 的地址编排让它们落到 0、2g、g、3g。
2. **第三支的旋转因子是 `-i·w1`，不是 `w3`**。
   教科书说用 `w3 = exp(-6πik/L)`，但那是"两层分开做"的写法；合并后应该是 `w3 = -i·w1`。

另外：radix-4 要求 `log2(N)` 是偶数。两个公开用例 256（2^8）、1024（2^10）都是偶数，
但保险起见奇数时退回 radix-2 路径。

### 4. 装载/写出也要向量化

`input` 的布局是 `[batch][复数]`，而计算用的布局是 `[下标][batch]`，中间要做一次转置。
朴素写法是双重标量循环——**f8 的 profile 显示这部分占了可观时间**。

用 NEON 的 4×4 转置：

```c
vtrnq_f32(r0, r1)  // 交错
vcombine_f32(...)  // 拼接低位/高位
```

配 `vld2q_f32`（一次load得到 de-interleave 的实部/虚部）和 `vst2q_f32`（交错写回）。
实测 f8 → f9：25.64 → 24.83 µs（16×256），66.22 → 62.91 µs（8×1024）。

## 三、硬约束（写错直接 0 分）

- **单线程**：不能用 OpenMP / pthread
- **不许运行时分配内存**：用 `static` 全局数组，禁 `std::vector` / `new`
- **禁外部 FFT 库**：FFTW 等一律不行

## 四、工作流

每改一版就跑：

```bash
bash tools/check.sh    # 必须出现 correctness: passed
bash tools/bench.sh    # 看 median_time_ms
```

卡住了看 `bash tools/profile.sh`，重点看两个指标：

- **IPC**（每周期指令数）：低于 1.5 说明是**延迟瓶颈**（依赖链太长，执行单元空转）→ 加宽 lane
- **l1d_mpki**：L1 数据缓存每千条指令的 miss 数，高了说明工作集太大 → 减宽

## 五、这次最大的一个意外发现：英文比中文省 token

同一个 tokenizer（DeepSeek-V3），表达**完全相同的内容**：

| | 字符数 | token | token/字符 |
|---|---|---|---|
| 中文 | 174 | 111 | 0.64 |
| 英文 | 266 | 82 | 0.31 |

**英文虽然字符多 53%，token 反而少 26%。** 因为 DeepSeek 的词表对英文技术文本的
BPE 压缩率高得多（`vectorization`、`butterfly` 这种词往往 1–2 个 token）。

整套手册：中文 510 token → 英文 440 token，省下 70 token ≈ m 从 1.36 提到 1.45。
按上面的计分公式，这相当于 P=0.6 时白拿 8–10 分。

**另一个坑**：英文写成 `description: fft kernel: cross-batch...` 会因为
**半角冒号+空格**被 YAML 当成键值分隔符，提交直接被 REJECTED。
旧的中文版用全角「：」反而没事。修法是换成 `-` 或加引号。
