# 06-rune 优化总结

## 题目与评分

- 任务：在线确定性调度（online deterministic scheduling）。给定一个固定的集群模型（若干机器，各有 CPU 容量、内存容量、能力标签 capabilities、每种任务类型的速度倍率）和一条按事件时间到达的任务流。`policy.py` 的 `choose_placements(observation)` 在每个决策点被调用，返回不超过 `max_batch_size` 个「任务 → 机器」的派发决定，或选择 DEFER 等下一个事件。全程确定性（同种子同结果），所以策略可以被精确复现和离线扫描。
- 硬约束（违反即该局作废）：机器必须可用（未停机）、能力标签覆盖任务要求、内存预留之和不超过内存容量。
- 软约束：**CPU 超载不报错，但机器上所有任务的 CPU 需求之和超过容量时，整机任务按比例变慢** —— 这是本场最大的得分陷阱。
- setup：同一决策点、同一台机器、同一类型的任务共享一次 setup；setup 时长同样受该机器速度倍率影响。重负载 profile 里 setup 占总时长的 34%~57%，因此「攒批」是核心杠杆。跨决策点不能共享 setup（用探针局验证过）。
- 评分：每个 profile 用 64 个确定性种子各跑一局取 makespan 均值 x，再算 `s = clamp(F(B−x)/(x(B−F)), 0, 1)`。F 是满分线（参考策略实测值 ×1.05 上取整），B 是零分线（F × 1.2）。18 个 profile 权重分 30/20/5/2/1 五档，原始权重合计 337；**OJ 上报时按 100/337 归一，总分是 100 分制**。

## 最终策略（policy.py）

三步贪心 + 三条全部经实测验证的规则：

1. **strict CPU：普通选择绝不让机器 CPU 超载**（`CPU_HEADROOM = 0.0`）。超载让整机任务按比例减速，代价远大于收益：同一批 9 个高权重 profile 上，严格不超载 155.6/270，放宽回填只有 136.3/270。
2. **type-packing 凑批**：同类型任务优先塞到本决策点已经放了同类型的机器上，蹭 setup 共享；凑批轮允许 CPU 超载到 `PACK_LIMIT = 1.25`（≈「最多再塞一个任务」，任务 CPU 需求多为容量的 1/4），失败则退回 strict 全局选择。扫描 1.0 / 1.125 / 1.25 / 1.375 / 1.5 / 2.0 / 无上限，1.25 是峰值；全 18 × 64 种子复核：L=2.0 → 209.3，L=1.25 → 228.5。
3. **稀缺优先稳定排序**：按「能接该类型的机器数」升序处理就绪任务（瓶颈类型先挑机器），同稀缺度用稳定排序保持到达顺序。全 18 × 64 种子：228.5 → 242.8。

另外保留基线里的亲和性规则：选「这台机器跑这种类型的速度倍率」最小的机器。一个都放不下就 DEFER，等下一个事件。

## 方法论：这些结论怎么来的

- **一切以 64 种子真均值为准**。踩过的坑：`run_scenario.py` 报告里 `results` 是「每种子一项」的列表，一开始读 `results[0]`（0 号种子单次结果）当分数，导致 8 种子和 64 种子跑出完全一样的数字。修正后同一策略从「237.2」变成真均值 **209.3**，差 28 分，连优化项的收益排序都变了（type-packing 单种子看着 +14.6，真均值只有 +1.2）。框架其实已在输出的 `metrics.candidate_makespan` 里算好均值，直接用即可。
- 每个改动都做 A/B 对照：同一批种子、同一脚本、只换策略文件，不凭直觉。本场直觉翻车三次：动态回填更差、停机规避更差、hold-back 延迟攒批四档全负。
- 变体策略放 `/tmp/policy_*.py`，正式的 `policy.py` 始终只保留「已实测」的唯一版本。

## 走过的弯路（教训）

1. **单种子口径骗人**（见上）——统计口径是这次最大的坑，真均值让「237.2」现出 209.3 的原形。
2. **tiebreak 用类型名字母序把 profile-18 打崩**：稀缺排序最初用「稀缺度 + 类型名」做 key，18 号均值暴涨 +881。改成稳定排序（同稀缺度保持到达顺序）后，18 号大赚 −342，17 号跨过满分线 −185。
3. **hold-back 延迟攒批**（等 K 个同类型任务到齐再一起派）：K=1..4 全部 ≥ 基线，空等的代价大于 setup 的节省。
4. **停机惩罚 / 瓶颈优先 / 纯分组**等针对 07 号的专项方向全部无法胜过基线，且多数伤害其它 profile —— 07 是结构性硬骨头（StageB 全集群只有 2 台机器能接，其中 1 台还会停机）。

## 最终成绩

- **OJ 最终评测：67.58 / 100**（原始权重口径 227.8 / 337），18 个算例全部 accepted / success，`scenario-valid` 全为 1。
- 本机同一策略、公开 seed-key、64 种子：242.8 / 337 = **72.05 / 100**。
- 两者相差 4.4 分，来源不是策略而是**评测换了一套种子**：满分线 F 定义为「参考策略实测 ×1.05」，所以均值离 F 不到 5% 的 profile，64 种子均值的毫厘漂移就会整块翻面。这次 OJ 上 profile-08（F=1330，本机 1274 → OJ 1383.8，−2.05 分）、06（−1.55）、17（−0.95）吃到反向漂移，profile-12/18 吃到正向漂移。**下一步的提升方向不是再找新启发式，而是鲁棒性：把尾部坏种子拉回来**（如 06 号 min=945 / max=1474 的 1.56 倍极差），而不是把中位数再压几十毫秒。
